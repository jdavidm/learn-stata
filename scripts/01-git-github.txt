1. What are Git and GitHub?

Git is version control software.
You can think of it as a time machine for your files: it lets you save snapshots of your work, go back to older versions, and see what changed over time.

[On screen: Switch to your web browser.]

[On screen: In the address bar, type https://git-scm.com/ and press Enter.]

This is the official Git website. This is where Git is documented, and it’s also where you can download Git if you ever need the command-line version.

Git itself:

Runs on your computer, locally.

Tracks changes to files in a repository (a folder that Git is watching).

Saves those changes as commits — snapshots with messages like “what changed and why.”

In this course, we’ll mostly interact with Git through GitHub Desktop, which gives you a nice GUI instead of typing commands into a terminal.

[On screen: Click around lightly on the Git homepage: point at “Documentation” and “Download” in the navigation bar.]

Now, Git has a lot of commands, but you only really need a small set to work effectively.

[On screen: In a new tab or the same tab, go to https://git-scm.com/cheat-sheet.]

Here’s an official Git cheat sheet.
This shows many of the most common commands, like:

git status to see what’s changed,

git add to stage changes,

git commit to save a snapshot,

git log to see your history.

We’re not going to type these manually in this class, but it’s useful to know that this is what GitHub Desktop is doing behind the scenes.

Now let’s talk about GitHub.

[On screen: In the address bar, go to https://github.com/jdavidm.]

GitHub is a website that hosts Git repositories in the cloud.
So the distinction is:

Git = the tool that tracks changes on your computer.

GitHub = the place where those Git repositories live online and where you can collaborate with other people.

Here you’re looking at my GitHub profile.

[On screen: Point to the list of repositories.]

Each of these is a repository — basically a project tracked with Git. Some are for teaching, some for research, some for code projects.

[On screen: Scroll down until the contribution graph (grid of squares) is visible.]

Down here you can see my contribution graph, sometimes called a punchcard-style view of my work. Each square represents how many contributions I made on a given day — things like commits, opening issues, or pull requests. The darker the square, the more activity that day.

So:

On your computer, you’ll work locally with Git (through GitHub Desktop).

When you’re ready to share your changes or back them up, you push them to GitHub, where they show up in a repository like these and contribute to this graph.

Now let’s see how that looks in practice using GitHub Desktop.

4. Tour of GitHub Desktop panes

Let’s walk through the main parts of GitHub Desktop.

1. Top bar

[On screen: Move your mouse along the top bar as you mention each item.]

Current repository: which project you’re working on.

Current branch: which version/line of development you’re on. In this class, you should almost always be on your branch, not main.

On the right side:

Fetch origin: checks if there are new changes on GitHub that you don’t have yet.

Push origin: sends your local commits up to GitHub.

If the branch is new, you may see Publish branch instead of Push. That uploads your branch to GitHub for the first time.

2. Left side: Changes / History

[On screen: Click on the Changes tab.]

The Changes tab shows all files you’ve modified but not yet committed.

[On screen: Click the History tab briefly.]

The History tab shows past commits with messages, dates, and who made them.

[On screen: Click back to the Changes tab so the modified file is visible.]

3. Center pane (diff)

[On screen: Click the changed file in the Changes list.]

When you click on a file in the Changes list, the center shows a diff:

Removed lines are highlighted.

Added lines are highlighted.

[On screen: Point with the mouse to the newly added line in the diff.]

This is how GitHub Desktop shows exactly what changed — this is Git’s “time machine” view of your code or text.

4. Bottom left: Commit box

[On screen: Move the mouse to the “Summary” and “Description” boxes.]

This is where you write a Summary and optional Description for your commit.

The button below (e.g., “Commit to <your-branch>”) creates the commit.

5. Making a commit (with a good summary)

Let’s commit the change we just made.

In the Summary box, you should always write something short but meaningful.

Bad summary: “stuff” or “changes”
Better summary: “Add note to GitHub demo file”

[On screen: Click in the Summary box and type:
“Add note to GitHub demo file”
Optionally type a sentence in the Description box.]

Once that looks good, I’ll click the commit button.

[On screen: Click “Commit to <your-branch>”.]

Notice that:

The file disappears from the Changes list, because there are no uncommitted changes now.

If I click over to History, I can see the new commit with my summary.

[On screen: Click the History tab and point at the new commit.]

That commit is now saved locally on my computer using Git.

This is how Git and GitHub work together:

Git: tracks your changes locally, as commits.

GitHub: stores those commits in a repository online, where they’re backed up and shareable.

And GitHub Desktop is the tool we use to bridge between the two without having to type Git commands ourselves.

That’s the basic GitHub Desktop workflow we’ll use all semester:

Make changes in your files

Check them in GitHub Desktop (Changes pane + diff)

Write a clear commit summary and commit

Push to GitHub so it’s saved and shared

We’ll build on this as we go, but if you can do these steps, you’ve got the core Git/GitHub skills you need for this course.
